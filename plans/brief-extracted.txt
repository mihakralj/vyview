1 Executive summary
vyview (working name) is a view-only web dashboard for a VyOS router. It gives a prosumer owner fast, visual access to
everything that VyOS op-mode and the underlying Linux system already know: interface and client traffic, firewall and
NAT activity, routing state, VPN health, services, QoS behaviour, hardware and flash health, the configuration and its
history, logs and derived events. It runs on the router itself as one small Go binary, renders HTML on the server, and
keeps pages live through a single Server-Sent Events (SSE) stream per open page using the Datastar hypermedia
framework. Styling comes from a build-time UnoCSS stylesheet and a subset of Font Awesome Free icons; time-series
charts use uPlot.
The dashboard is deliberately read-only by construction. It is a better window into the router, not a second control
plane. There is no code path that writes configuration, clears counters, resets sessions, reboots, generates keys, adds
images or executes arbitrary commands. This is enforced in the architecture (no state-changing routes, an allowlist of
read-only collectors, no shell) rather than by convention, because the VyOS HTTP API's keys grant full access and cannot
be scoped to read-only.
1.1 What it is
  A single-router, LAN-only dashboard: 15 top-level sections, roughly 70 deep-linkable views, every widget labelled
with the exact command, netlink call or file it came from.
 A live and historical view: 1-second live rings in RAM, and rollups at 10 s, 1 min, 5 min and 1 h kept for up to two
years with min/avg/max/p95, sized to stay within flash-wear and memory budgets computed in Section 10.
 A fast view: server-rendered first paint in under 300 ms on the LAN, an initial payload of about 134 KB compressed
(64 KB with system fonts), and idle streaming estimated at 1.0 % of one Cortex-A72 core.
 A pluggable view: optional modules (for example the ASK2 hardware-offload dataplane module for the LS1046A)
declare their collectors and pages. When a module's data source is missing, as on stock x86 VyOS, its pages are
hidden or show only the generic kernel equivalents.

1.3 Key design principles (summary)
 1. Read-only by construction. No mutating HTTP verbs, no write collectors, executables called only from an allowlist
with fixed argument templates, no shell, and identifiers validated against known sets.
2. Source transparency. Every number has a source chip naming the op-mode command, Linux command, netlink
family or file, with a copy button. This builds trust and helps the user learn VyOS.
3. Overview first, zoom and filter, then details on demand (Shneiderman's mantra), with progressive disclosure on
every page.
4. One shared time range across all charts on a page, synchronised crosshair and brush-to-zoom, and event
annotations (commits, reboots, link flaps, routing changes).
5. Live by default, pausable. While paused, a counter shows how many updates are pending.
6. Fixed status semantics. ok / warn / crit / info / unknown use a colour-blind-safe palette and always pair colour with
an icon and text.
7. Budgets are requirements. Time to answer in 3 clicks or fewer; first paint under 300 ms on the LAN; under 3 % of
one A72 core while idle-streaming; under 40 MB RSS; flash writes only as batched rollups.
8. Accessible and self-contained. WCAG 2.2 AA, keyboard-first, and no CDN or internet dependency: the dashboard
must work during an internet outage, which is when it is needed most.
1.4 Architecture at a glance
Figure 1 — vyview architecture. Browsers talk HTTPS (GET and SSE only) to one Go process on the router. The process reads from the
kernel, FRR, VyOS op-mode, journald, the Kea control socket and the running configuration through allowlisted collectors. It never calls
mutating APIs.
The recommended implementation is a static Go binary using the official Datastar Go SDK. Collectors feed a normalised
in-memory state model and RAM ring buffers. A rollup engine writes batched multi-resolution history, an SSE hub fans
out changes to subscribed pages, and renderers produce HTML fragments that Datastar morphs into the DOM by
element id. Chart data travels as Datastar signals into small custom elements that wrap uPlot. A privileged helper process
exposes only fixed read-only calls, so the web-facing process holds no capabilities (Section 11).

2 Goals, non-goals, personas and jobs-to-be-done
2.1 Goals
  Answer the common questions a VyOS owner has in three clicks or fewer, without SSH.
 Make history first-class: show what changed and when, and connect it to commits, reboots and link events.
 Expose everything op-mode knows in a navigable, searchable form, including the configuration (redacted) and its
diffs.
 Run comfortably on an embedded ARM64 router (LS1046A, eMMC/SD storage) and on x86 VyOS, with no external
dependencies.
 Make the optional hardware-offload dataplane (ASK2) observable: is offload engaged, how much traffic takes the
hardware path, and where are queues and buffers under pressure.
 Be pleasant on a desktop, usable on a phone, and legible on a wall-mounted display.
2.2 Non-goals (v1)
  Any write or action capability (Section 1.2). Alert notification delivery. Multi-router fleet views.
 Replacing Grafana/Prometheus for long-term analytics at scale. vyview can export to them but must work
standalone.
 Deep packet inspection UI or full Suricata alert management. vyview shows counters and verdict summaries only.
 Internet-exposed operation. vyview is designed for LAN or management VRF access, and optionally behind a VPN.

3 Design principles
The principles below are binding. Each one ends with the concrete rule a developer can test against.
3.1 Read-only by construction
The safest write path is one that does not exist. The HTTP router registers only GET handlers (pages, fragments, assets)
and GET SSE streams. Collectors are typed functions that return data. Where an external executable is unavoidable, it is
called via exec.CommandContext with a fixed path and an argument template from an allowlist, never through
/bin/sh. Identifiers that reach a collector (interface names, chain names, peer keys, revision numbers) are validated
against the set currently known to the state model, so they are never free text. Rule: a static test enumerates all
registered routes and fails if any accepts a method other than GET/HEAD. A second test greps the binary's collector
registry against the allowlist.
3.2 Source transparency
Every card, table and chart shows a source chip, for example show interfaces ethernet eth0 or nft -j list
ruleset. Hovering shows the exact invocation, cadence, last refresh time and parser; clicking copies the command so
the user can reproduce it in the CLI. Where vyview uses netlink instead of spawning a tool, the chip shows the equivalent
CLI command and a 'via netlink' badge. Rule: a widget without a declared source fails the template lint.
3.3 Overview first, zoom and filter, details on demand
Every section starts with a summary (KPI strip, status counts), then a filterable list, then a detail drawer or page.
Drill-down never loses context: breadcrumbs, the time range and filters persist in the URL. Rule: every list row is a link to
its detail view, and every detail view links back to its list with filters intact.
3.4 Progressive disclosure
Default views show the 5–8 most useful fields. Rarely needed fields (driver counters, LSDB contents, raw JSON) are
behind tabs, 'show all counters' toggles, or a 'raw output' panel that shows the unparsed command output. Columns can
be added with a column chooser, and the choice is stored in localStorage.
3.5 One shared time range
A page has exactly one active time range (preset or absolute). All charts on the page follow it, crosshairs are synchronised
across charts, and brushing on any chart zooms all of them. A 'compare to previous period' toggle overlays the prior
equal-length window as a dashed series. The range is a Datastar signal ($range) mirrored in the URL (?range=24h or
?from=…&to=…).
3.6 Live by default, with pause
Pages stream updates by default. Pause (space bar or toggle) freezes the view so the user can read or copy. The stream
keeps running and the top bar shows 'N updates pending'. Resume applies the latest state in one morph rather than
replaying every update. A stale-data badge appears on any widget whose last update is older than 2 × its cadence.
3.7 Status colour semantics
Five statuses are used: ok, warn, crit, info and unknown. Their colours come from a colour-blind-safe palette (Section
6.1). Status is never shown by colour alone: it always pairs with an icon shape and a text label, and charts use shape and
dash as well as hue for thresholds.
3.8 Density control
Three densities (comfortable, compact, wall) change spacing, row height and type scale via CSS variables. Compact suits
the owner on a big monitor. Wall raises the type scale and hides secondary columns for kiosk use.

4.3 URL and state model
URLs are hierarchical and human-readable (/interfaces/eth0?range=6h&tab=optics). The server treats the URL as
the source of truth on first load and renders the complete page, so a deep link paints correctly without JavaScript.
Datastar then takes over: the page's signals ($range, $live, $filter, $sort, $sel) are initialised from the URL with
data-signals. A small history.replaceState effect keeps the URL in sync as signals change, and the SSE stream is
reopened with the new signals. The full route map is in Appendix E.

6.5 Card anatomy
  Header: icon (Font Awesome, 14 px, muted) · title · optional status dot · source chip right-aligned · overflow menu
(export, copy link, view as table).
 Value block (KPI cards): primary value with unit, delta vs previous period (up/down arrow with semantic colour only

 Body: chart, table or list. Charts have no titles of their own; the card title is the chart title.
 Status edge: 3-px left bar in the status colour when the card represents a health state.
 Footer (optional): 'updated 2 s ago', stale badge, pagination.
6.6 Tables
  Sticky header; zebra striping at 4 % contrast; row hover; selected row uses an accent left bar and a tinted background.
 Virtual scrolling for conntrack and lease tables (10k–100k rows): fixed row height, a window of visible rows + 10
overscan, and the scroll position mapped to an offset signal. The server returns only the visible slice (offset, limit)
for sets above 2,000 rows. Below that, the full set is sent once and filtered client-side.
 Column chooser (persisted per table in localStorage), resizable columns, right-aligned numerics with tabular
numerals.
 IPs, MACs, keys, commands and paths in monospace; click-to-copy with a toast; long values truncated in the middle
(2001:db8:4f2a…::23) with the full value on hover.
 Structured filter chips (proto = tcp, src ∈ 192.168.10.0/24) parsed and validated server-side; text search as a
fallback.

9 Architecture and implementation
9.1 Recommendation
Build vyview as a single static Go binary that contains the collectors, the time-series store, the web server and all assets.
It runs on the router as an unprivileged systemd service bound to the LAN or management VRF, and uses the official
Datastar Go SDK (Go is the SDK reference implementation). Go fits this job well: static cross-compiles for arm64 and
amd64, mature netlink, nftables, WireGuard and journald libraries, cheap goroutines for SSE fan-out, go:embed for
assets, and a small, predictable memory footprint with GOMEMLIMIT.
 Alternative
Why not (for v1)
Python (Flask/FastAPI) inside VyOS'
Python environment
Reuses vyos.opmode directly, but Python startup (~0.5–1 s per call on A72) and memory (~40–60 MB per
process) do not fit the budgets. Also couples to VyOS internals and their upgrades.
Grafana + Prometheus + exporters on
the router
Excellent for metrics, but heavyweight (hundreds of MB), not a navigable op-mode/config explorer, and
writes heavily to flash. Kept as an optional external integration (Section 10.6).
SPA (React/Vue) + JSON API
More client JS (typically 200–500 KB), duplicated state logic, harder CSP. Datastar keeps the server
authoritative with a ~11 KB client.
Rust (axum)
Viable and lean; the Datastar Rust SDK exists. Go chosen for the official SDK, faster iteration and library
breadth (vishvananda/netlink, google/nftables, wgctrl, go-systemd).

9.4 The VyOS HTTP API: optional, and never for writes
VyOS exposes an HTTP API (set service https api …) with REST endpoints that are all POST with form fields data
and key: /retrieve (ops showConfig with a path list where an empty list returns the whole config, returnValues,
exists), /show (runs op-mode show commands and returns text), plus mutating endpoints /configure,
/config-file, /image, /generate, /reset, /reboot and /poweroff. GET /info is the only unauthenticated
endpoint. A GraphQL API also exists (introspection is off by default; JWT authentication is an option).
A VyOS API key grants full access to the API. There is no read-only key or per-endpoint scope. Any component holding a key
can reconfigure, reboot or reimage the router. vyview therefore does not need, store or use an API key in its default,
on-box mode.
On-box mode (default): vyview reads local sources directly (netlink, files, sockets, allowlisted read-only commands) and
does not touch the API. Remote mode (optional, for running vyview off-box or for a future fleet view): vyview may call
the API through a client wrapper that exposes only /retrieve with showConfig/returnValues/exists, /show with
paths from the allowlist, and GET /info. The wrapper has no method that can construct any other endpoint (the URL
set is a compile-time constant), and an outbound request filter rejects any other path as defence in depth. The key is
stored in a root-owned file readable only by the helper, and the UI warns that the key is full-access. Calling /configure,
/config-file, /reset, /reboot, /poweroff, /generate or /image is impossible by construction, and a unit test
asserts that the string set of reachable paths contains only the allowed ones.

10 Time-series storage and retention
History is what turns a status page into a diagnostic tool. The storage design has to give up to two years of history on an
eMMC/SD-backed router without wearing out the flash or using much memory. The approach: RAM rings for live data, a
tmpfs hot tier for the last 48 h, and compact flash tiers written in time-major blocks once per minute.

11.2 Read-only guarantees
 1. No write endpoints: the HTTP mux is built from a declarative route table and a test asserts that every route is
GET/HEAD.
2. No mutating collectors: collectors implement only Collect(); netlink sockets are opened for dump requests only.
The helper uses message types from a read-only allowlist (for example RTM_GET*, NFT_MSG_GET*,
IPCTNL_MSG_CT_GET*) and rejects anything else before it reaches the kernel.
3. Allowlisted executables only, no shell, typed placeholders validated against known sets.
4. Validated identifiers: interface names, chain names, peer keys, revisions and neighbour addresses must exist in the
current state model.

11.5 Sessions, CSRF and request rules
  Sessions: random 256-bit ids, server-side store in RAM, idle timeout 12 h, absolute 7 d, rotation on login.
 Cookies: Secure; HttpOnly; SameSite=Strict; Path=/. Because no state-changing endpoints exist, CSRF has
no target. Login uses POST with a CSRF token; it is the only POST, and logout is the other non-GET exception, both
outside the data plane.
 Every SSE/fragment request re-validates the session. Signals are parsed with a strict schema (enums for range, regex
for ids, numeric bounds for offsets/limits) and unknown fields are rejected.
 Rate limits: login 5/min per IP with exponential lockout; search 10/s per session; export 1/s per session; new streams
10/min per session.
11.6 Content Security Policy and Datastar
Datastar evaluates the expressions in data-* attributes by compiling them into functions at runtime, which requires
'unsafe-eval' in script-src. This is a real weakening: if an attacker can inject an attribute such as data-init into
the page, it executes. The mitigation is to make injection impossible and contain the impact:
  **Never reflect user input into data-* attribute values or attribute names.** All Datastar expressions are static
strings in templates; dynamic values are passed as signals (JSON-encoded by the server) or escaped text, never
concatenated into expressions. A template lint fails the build on any data-* attribute containing a template action.
 Contextual auto-escaping (html/template/templ) for all text and attributes; sanitise log lines and hostnames as text
only.
 CSP: default-src 'none'; script-src 'self' 'unsafe-eval'; style-src 'self'; img-src 'self'
data:; font-src 'self'; connect-src 'self'; manifest-src 'self'; worker-src 'self';
base-uri 'none'; form-action 'self'; frame-ancestors 'none'; object-src 'none'. No
'unsafe-inline' for scripts; the tiny theme pre-paint script uses a hash source.
 Additional headers: X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer,
Permissions-Policy denying all unused features, Cross-Origin-Opener-Policy: same-origin, HSTS on the
TLS listener.
 Track Datastar's CSP guidance across releases. If a CSP-friendly build without eval becomes available, adopt it and
drop 'unsafe-eval'.
11.7 Network exposure and TLS
  Listen only on explicitly configured addresses (default: the LAN bridge address and/or management VRF). Never on
WAN interfaces. Start-up refuses to bind to 0.0.0.0/:: unless a firewall check confirms that the input filter protects
the port.
 VRF: bind the socket to the VRF device (SO_BINDTODEVICE) or run under ip vrf exec mgmt via the unit.
 TLS: certificate and key from VyOS PKI (pki certificate <name>); TLS 1.3 preferred, 1.2 allowed with AEAD
suites; automatic reload on certificate change.

    var sig OverviewSignals

        http.Error(w, "bad signals", http.StatusBadRequest); return
    }
    sse := datastar.NewSSE(w, r)                         // sets text/event-stream headers, flushes per
      event
    sub := s.hub.Subscribe(r.Context(), session(r), "overview", sig)
    defer sub.Close()

// vy-chart: minimal custom element wrapping uPlot, fed by a Datastar signal attribute
class VyChart extends HTMLElement {
  static observedAttributes = ['data-series'];
  connectedCallback() { this.u = new uPlot(this.opts(), [[]], this); }
  attributeChangedCallback(_, __, v) {
    const d = JSON.parse(v || 'null'); if (!d || !this.u) return;
    if (d.append) { /* push points, trim to window */ this.appendPoints(d); }
    else { this.u.setData([d.t, d.rx, d.tx]); }
  }
  opts() { return { width: this.clientWidth, height: 240, cursor: { sync: { key: 'page' } }, series: [{},
      {label:'rx'}, {label:'tx'}] }; }
}
customElements.define('vy-chart', VyChart);

Appendix F — Glossary
 Term
Meaning
AQM
Active Queue Management: dropping or marking packets early to control queueing delay (e.g. CoDel, CAKE).
ASK2
The owner's hardware-offload work for VyOS on NXP DPAA1 (flow offload, CEETM QoS, WireGuard acceleration,
ACL/DDoS drop, Suricata shunt).
BFD
Bidirectional Forwarding Detection: fast liveness detection between routing neighbours.
BMan / QMan / FMan
NXP DPAA1 Buffer Manager (buffer pools), Queue Manager (frame queues, portals, congestion) and Frame Manager
(packet parsing, classification, MACs).
Bufferbloat
Excess latency caused by oversized, unmanaged buffers under load.
CAKE
Common Applications Kept Enhanced: a Linux qdisc combining shaping, flow isolation, AQM and DiffServ tins.
CEETM
Customer Edge Egress Traffic Management: DPAA1 hardware egress scheduling and shaping with class queues and
committed/excess rates (CR/ER).
Conntrack
Linux connection-tracking table used by stateful firewalling and NAT.
DOM
Digital Optical Monitoring: SFP/SFP+ diagnostics (power, temperature, voltage, bias) per SFF-8472/8636.
Flowtable
nftables fast path that bypasses the classic forwarding path for established flows; may be hardware-offloaded.
FIB / RIB
Forwarding Information Base (kernel routes used to forward) / Routing Information Base (all routes known to the
routing daemon).
Morphing
Updating the DOM by diffing new HTML against existing elements (by id) instead of replacing them, preserving focus
and state.
op-mode
VyOS operational mode commands (show …), implemented largely by Python scripts in the vyos.opmode framework.
p95
95th percentile of samples within a rollup slot.
PSI
Pressure Stall Information: Linux metrics for CPU, memory and I/O contention.
Rollup
Aggregation of fine-grained samples into coarser time slots (min/avg/max/p95).
Signals (Datastar)
Reactive client-side state referenced as $name in data-* expressions; sent to the backend with requests unless
underscore-prefixed (private).
SSE
Server-Sent Events: a one-way HTTP streaming protocol (text/event-stream) from server to browser.
Tier
A retention level with a fixed step and span.
Time-major layout
Storage layout where all series for one time slot are contiguous, minimising pages touched per write.
VRF
Virtual Routing and Forwarding: an isolated routing table and interface set.
WAF (flash)
Write amplification factor: ratio of NAND writes to host writes.
